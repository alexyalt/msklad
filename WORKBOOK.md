# WORKBOOK

Журнал проекта msklad (Android-сканер штрихкодов для МойСклад). Файл сжат 2026-11-28 после
версии 1.6.1: убраны хеши коммитов, номера CI-прогонов и пошаговые записи «сделал то, сделал это» —
полный ход работы остаётся в истории git (`git log -p -- WORKBOOK.md`). Здесь только то, что
нужно знать, чтобы продолжать разработку.

Правила работы агента — `AGENTS.md`, техзадание — `docs/TZ.md`, устройство кода — `ARCHITECTURE.md`.

## Состояние проекта

- `main`, версия **1.7.0** (`versionCode` 12), тег `v1.7.0`. Один модуль `app` (Kotlin, minSdk 24,
  compileSdk/targetSdk 34, ViewBinding, Retrofit + Gson + OkHttp, CameraX, ML Kit barcode-scanning).
- Три документа: «Перемещение» `entity/move`, «Оприходование» `entity/enter`, «Списание» `entity/loss`.
- Сборка/проверка — только GitHub Actions (`assembleDebug`); локально `./gradlew` не запускается,
  unit-тестов в проекте нет, проверка — сборка + ручной сценарий на тестовом аккаунте.
- Тестовый аккаунт МойСклад (пустая база для разработки) — реквизиты у владельца проекта,
  в репозиторий не пишутся.
- Печать этикеток: локальный Flask-сервер `labelserver/` для Windows (опционально).

## CI и релизы

- `.github/workflows/android-ci.yml`: сборка на `push` в `main` и на любой `pull_request`,
  артефакт `msklad-debug-apk`; при пуше в `main` дополнительно публикуется служебный релиз `latest`
  (файл `msklad-debug.apk`). Пайплайн с версионированием не связан — не ломать его.
- Версионный релиз делается отдельно от CI: тег `vX.Y.Z` на коммите `main`, релиз «Версия X.Y.Z»,
  APK из артефакта того же коммита, переименованный в `msklad-<версия>-debug.apk`. Прошлые релизы
  не перезаписываются. SemVer: major — несовместимо, minor — функциональность, patch — исправления.
- Перед merge обязательна успешная сборка PR; merge в `main` — только после разрешения конфликтов.

## Знания по API МойСклад (набитые грабли)

- Фильтр `id`: только UUID. Полный href в `id=` → 400 (код 1014); несколько значений — через `;`,
  не через `,`. Отсюда `uuidOf(href)`, батчи по 50 (`ID_BATCH`).
- `report/stock/all`: фильтр `store=<полный href склада>`, не голый id. `offset`/`limit`
  (1000 на страницу, максимум 20 страниц). Строка отчёта — товар напрямую: href товара лежит в
  `meta.href` либо в `assortment.meta.href`, полей assortment в ответе нет.
- Товар без движения на складе в `report/stock/all` отсутствует вовсе (нулевой остаток не отдаётся).
  Отрицательный остаток (пересорт) сервер отдаёт — поэтому фильтр `qty > 0` в коде обязателен,
  на поведение API не рассчитывать.
- `expand` (`positions.assortment`, `store`) поддерживается не везде: при 400 запрос повторяется без
  expand, имя склада дочитывается `entity/store/{id}`, единица измерения — из справочника `entity/uom`.
- `uom` у товара — только meta-ссылка, имени нет; у части товаров она не задана → `DEFAULT_UOM = "шт"`.
- Оприходование — это `entity/enter`; `entity/supply` — другой документ («Приёмка»).
- Добавление/удаление позиции: GET документа + PUT `entity/{type}/{id}` целиком.
- Лимит частоты 2 запроса/с (`RateLimitInterceptor`), на 429 — пауза и повтор.
- `Accept-Encoding: gzip` добавляет OkHttp сам и сам распаковывает ответ.

## Открытые задачи (на следующую итерацию)

- Товар без движения на складах перемещения и не входящий в позиции документов не попадает в
  офлайн-снимок → офлайн-оприходование его невозможно («не найден в локальной копии»). Это **штатное
  ограничение**: в снимок копируются только положительные остатки двух складов перемещения, полную
  номенклатуру не догружать (см. `AGENTS.md`, раздел «Офлайн-снимок остатков»). Решение — онлайн-режим
  или предварительное оприходование товара на склад.
- Офлайн-остатки ведутся по складам перемещения: оприходование и списание меняют остаток
  склада-источника, даже если в их документах указан другой склад (на тестовом аккаунте склады совпадают).
- Офлайн-снимок — плоская копия на момент загрузки; конкурентные изменения на сервере не мержатся,
  конфликт разрешает сервер и показывает ошибку целиком.
- Признак «не принято сервером» (красная строка журнала) живёт только в памяти ViewModel: после
  перезапуска экрана строки остаются жирными, краснеют после следующей синхронизации.
- Нет юнит/инструментальных тестов; вёрстка и работа на устройстве проверяются вручную.
- Из ревизии 1.7.0 (не делалось намеренно): `docs/TZ.md` описывает только перемещение — переписывать ТЗ
  без запроса пользователя не стали; `OfflineStore.load()` без валидации схемы Gson; unit-тестов нет.
