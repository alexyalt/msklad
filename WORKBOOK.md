## 2026-11-20 (API-слой)

- Добавлены `api/MoySkladApi.kt` (Retrofit), `api/ApiFactory.kt` (Basic Auth, таймауты; `Accept-Encoding: gzip` добавляет OkHttp автоматически и сам распаковывает ответ), `api/ApiException.kt` (русские тексты ошибок 401/403/404/429/сеть), `api/Json.kt`, `data/MoveRepository.kt` (поиск перемещения по номеру или UUID, поиск товара, остатки, добавление позиции через GET+PUT).
- Расхождения с ТЗ (осознанные):
  1. Поиск товара: сначала `filter=search=<код>` как в ТЗ, при пустом результате или 400 — `?search=<код>`, затем `filter=barcode=<код>`. Документация API неоднозначна, на реальном API не проверялось (нет учётных данных).
  2. Отчёт остатков: в фильтр подставляется href товара/склада, а не голый id (так требует API). Для модификаций используется `variant=` и `groupBy=variant`.
  3. Если товар уже есть в перемещении, количество существующей позиции увеличивается, а не добавляется дубль. PUT отправляет все позиции (иначе API заменит коллекцию), поля существующих позиций сохраняются.
  4. Остатки считаются по значениям до PUT: источник = остаток − количество, получатель «было» и «стало» = остаток + количество. Так результат не зависит от того, проведён документ или нет.

## 2026-11-20 (правки 1.1, шаг 1: поиск товара и проверка остатка)

- Причина добавления «Товар 1» на случайный код (проверено на реальном API тестового аккаунта): запасной запрос `entity/assortment?search=<код>` игнорируется и возвращает все товары, приложение брало первый. Также `filter=search=1` находит 12 товаров по вхождению в название.
- `MoveRepository.findProduct` теперь ищет только точными фильтрами по порядку `barcode=`, `code=`, `article=` (проверено: `barcode` и `code` дают точное совпадение, мусорный код даёт 0 строк). Это отступление от ТЗ п. 6.2 (там `filter=search=`), сделано осознанно: `search` даёт неточные совпадения. Параметр `search` убран из `MoySkladApi.assortment`.
- Проверка остатка: если количество больше остатка на складе-источнике, добавление не выполняется, ошибка «Недостаточно товаров (на складе: N)». Для проведённого перемещения (`applicable=true`, именно такое в тестовом аккаунте) остаток из отчёта уже учитывает существующие позиции; для непроведённого из остатка вычитается количество этого товара, уже лежащее в документе. Остаток источника после операции и «стало» на получателе считаются по тем же правилам.
- Добавлен `data/Format.kt` (`formatQuantity`).
- Проверка: временный JUnit-тест с MockWebServer (6 сценариев: мусорный код, «1», нехватка остатка, ровно весь остаток, непроведённый документ с позицией, отрицательный остаток), 6 из 6 прошли локально, тест в репозиторий не добавлен. На реальном API проверены только запросы поиска (чтение); запись позиций с проверкой остатка на реальном API не запускалась.
- В тестовом аккаунте на «Основном складе» есть отрицательные остатки (min −122), возникшие из-за прежнего поведения; я их не менял.
